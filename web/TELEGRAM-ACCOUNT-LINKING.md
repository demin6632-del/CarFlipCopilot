# AUTOFLIP — безопасная привязка Telegram-аккаунта к игровому профилю

Статус: проектирование. Этот документ не создаёт таблицы, не меняет базу и не включает вход на сайт.

## Что обнаружено в текущем коде

- Игровые профили хранятся в `autonomous_game_state` с первичным ключом `chat_id`.
- Telegram-бот при обработке сообщения получает одновременно `message.from.id` (пользователь) и `message.chat.id` (чат), но текущая логика игры передаёт в игровой модуль именно `message.chat.id`.
- В текущей схеме нет подтверждённой постоянной связи Telegram user ID с игровым chat ID.
- `load(chat, firstName)` не является безопасным read-only запросом: при отсутствии профиля он создаёт его, а при загрузке может нормализовать и синхронизировать состояние. Его нельзя вызывать из GET-обработчика сайта.
- Проверка Mini App `initData` подтверждает Telegram user ID, но сама по себе не доказывает, какой игровой профиль принадлежит этому пользователю.

Поэтому сайт не должен подставлять `user.id` в поле `chat_id`, принимать `chat_id` от браузера или искать профиль только по совпадению чисел.

## Предлагаемый безопасный сценарий привязки

1. Пользователь открывает Mini App. Сервер проверяет подпись и свежесть `initData`.
2. Если привязка ещё не существует, сервер создаёт одноразовый случайный код привязки (не менее 128 бит энтропии). В БД хранится только хеш кода, Telegram user ID, срок действия и статус.
3. Mini App показывает короткую инструкцию: открыть личный чат с официальным AUTOFLIP-ботом и отправить `/link КОД`.
4. Бот принимает команду только из личного чата (`chat.type === "private"`) и проверяет, что `message.from.id` совпадает с Telegram user ID, для которого сервер выпустил challenge.
5. В одной транзакции сервер блокирует challenge, проверяет хеш, срок действия и отсутствие использования, затем создаёт связь `telegram_user_id → private_chat_id`, помечает challenge использованным.
6. Уникальные ограничения запрещают привязать один Telegram user ID к нескольким игровым профилям и один private chat ID к нескольким Telegram user ID.
7. Mini App обновляет сессию и получает только свой профиль через серверный mapping. Клиент не передаёт идентификатор владельца в запросах.

Принципиально важно: связь подтверждается входящим сообщением от того же Telegram-пользователя в его личном чате с ботом. Не нужно полагаться на равенство чисел `user.id` и `chat.id`.

## Предлагаемые таблицы (не миграция)

### `autonomous_telegram_account_links`

- `telegram_user_id` — BIGINT PRIMARY KEY.
- `private_chat_id` — BIGINT NOT NULL UNIQUE.
- `linked_at` — timestamptz NOT NULL DEFAULT now().
- `updated_at` — timestamptz NOT NULL DEFAULT now().

### `autonomous_telegram_link_challenges`

- `id` — UUID PRIMARY KEY.
- `telegram_user_id` — BIGINT NOT NULL.
- `token_hash` — BYTEA NOT NULL UNIQUE.
- `expires_at` — timestamptz NOT NULL.
- `used_at` — timestamptz NULL.
- `created_at` — timestamptz NOT NULL DEFAULT now().

Требования к реализации: короткий TTL (например, 5 минут), ограничение частоты выдачи кодов и попыток, хранение только хеша, атомарное однократное использование, очистка просроченных challenges, отсутствие кода и полного initData в логах. Повторная привязка и смена профиля требуют отдельного подтверждённого сценария с аудитом; нельзя автоматически перезаписывать существующую связь.

## Сессия Mini App после привязки

- Сервер выдаёт случайный непрозрачный session ID; в БД хранится только его хеш.
- Cookie: `HttpOnly; Secure; SameSite=Lax` (или более строгая настройка, если она совместима с Telegram WebView).
- Короткий срок жизни, ротация, отзыв, защита CSRF для POST/PUT/DELETE, rate limits.
- Telegram initData используется для входа/обновления сессии, но не передаётся дальше по всем API-запросам.
- Каждый запрос получает `private_chat_id` только из проверенной серверной сессии.
- Ответы API формируются из allowlist-полей. Полный JSONB, внутренние chat IDs, ledger и registry IDs браузеру не возвращаются.

4. Реализовать read-only API, которое использует только подтверждённую привязку и не вызывает `load()`.
5. Добавить session store, CSRF и security tests.
6. Только после отдельного разрешения владельца — preview-интеграция на изолированной тестовой БД. Production и live bot не менять без отдельного разрешения.

## Запреты

- Не считать `telegram_user_id === chat_id` доказательством владения.
- Не принимать `chat_id`, user ID, owner ID или роль из тела/параметров запроса как источник полномочий.
- Не выдавать привязку только по username: username изменяем и не является секретом.
- Не разрешать привязку по пересланному сообщению, скриншоту или неподтверждённому коду.
- Не раскрывать, существует ли чужой игровой профиль, при неудачной привязке.
- Не включать ИИ-администратора/аналитика рынка в пользовательский API.
- Не трогать 3D-этап.
